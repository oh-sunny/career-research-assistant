# 좋은 직무 학습 자료 레퍼런스 분석

상태: 사용자 확인 완료

이 문서는 사용자가 좋다고 판단한 자료에서 수집 기준을 한 번 추출한 기록입니다. 실제 수집 실행에서는 이 문서를 매번 다시 분석하지 않고, `collection-policy.md`에 반영된 확정 기준만 사용합니다.

아래 자료들은 QA, 데이터 분석, 디자인 등 현재 관심 직무가 아닌 사례도 포함합니다. 해당 직무의 자료를 수집하자는 뜻이 아니라, **좋은 직무 학습 자료가 일을 설명하는 방식**을 파악하기 위한 레퍼런스입니다.

## 자료별 분석

### 1. 쏘카 QA는 무슨 일을 하고 어떻게 일하나요?

- 링크: https://tech.socar.kr/qa/2022/03/18/probationary-period_QA
- 관련 직무: QA
- 좋았던 이유: QA를 단순 테스트 업무로 설명하지 않고, 프로젝트 참여 시점부터 계획 수립, 테스트 케이스 작성, 이슈 기록, 결과 공유, 배포 후 모니터링까지 전체 업무 흐름을 보여줍니다. 개발자·기획자·디자이너와 무엇을 협의하는지, QA Plan과 버그 리포트에 무엇을 기록하는지도 구체적입니다.
- 추출한 특성: **업무의 시작과 끝**, 반복 업무, 산출물, 협업 대상, 판단 범위가 함께 드러나는 자료가 직무 이해에 유용합니다.

### 2. 사례로 보는 모바일 자동화 테스트를 통한 모니터링

- 링크: https://tech.kakaopay.com/post/ifkakao2022-mobile-automation-test-monitoring/
- 관련 직무: QA
- 좋았던 이유: 신규 기능 구현, 유지보수, 모니터링이라는 반복 업무를 구분하고, 실패 알림을 받은 뒤 장애인지 판단해 공유하는 과정까지 설명합니다. 도구 소개에 그치지 않고 안정성과 빠른 원인 파악이라는 현업의 고민이 드러납니다.
- 추출한 특성: 사용 도구보다 **왜 그 절차가 필요하고 담당자가 어디에서 판단하는지**를 보여주는 자료를 우선합니다.

### 3. 쏘카 데이터 그룹 데이터 사이언티스트 인턴 후기

- 링크: https://tech.socar.kr/data/2020/08/20/socar-data-group-intern-review
- 관련 직무: 데이터 분석
- 좋았던 이유: 이용 시간 감소라는 하나의 수치만 보고 결론을 내리지 않고, 매출·연령·예약 위치와 운영 담당자의 맥락을 함께 확인해 실제 차량 배치 판단으로 이어가는 사례가 있습니다. 분석 결과를 기록하고 동료와 논의하는 방식도 함께 보여줍니다.
- 추출한 특성: 데이터나 현상을 나열하는 데서 끝나지 않고 **해석의 함정, 추가 확인, 현업 지식, 최종 행동**이 연결되는 자료가 좋습니다.

### 4. 에이전시 출신 디자이너, 토스에서는 어떻게 일할까?

- 링크: https://toss.im/career/article/toss-pd
- 관련 직무: 프로덕트 디자인
- 좋았던 이유: 질문 구성이 담당 역할, 이전 환경에서 얻은 역량, 사용자 데이터가 부족할 때의 접근, 조직 환경의 차이, 실제 프로젝트 성과와 성장으로 이어집니다. 직무명만 설명하기보다 서로 다른 환경에서 일하는 방식이 어떻게 달라지는지를 묻습니다.
- 추출한 특성: **업무 맥락에 따라 판단과 접근이 어떻게 달라지는지** 보여주는 현직자 인터뷰를 우선합니다.

### 5. 안녕하세요! AI UX라이터 제민희입니다. 무엇을 도와드릴까요?

- 링크: https://techblog.woowahan.com/23836/
- 관련 직무: UX Writing, Product
- 좋았던 이유: 반복 검수와 요청 병목이라는 실제 문제를 좁히고, 규칙 기반 방식의 한계와 실패를 인정한 뒤 다른 방법으로 전환하는 과정을 공개합니다. 직무 간 이해 부족, 기술적 제약, 기준 변경 등 결과물 뒤에 있는 고민이 구체적입니다.
- 추출한 특성: 완성된 성공 사례만 소개하기보다 **문제 정의, 제약, 실패, 방향 전환과 배운 점**이 드러나는 자료를 높게 평가합니다.

### 6. 비개발자로 회의봇 만들기는 처음이라

- 링크: https://careers.daangn.com/blog/post/%EB%8B%B9%EA%B7%BC-%EC%9D%B8%ED%84%B4-%ED%9A%8C%EC%9D%98%EB%B4%87-%EB%8B%B9%EB%B2%88%EC%9D%B4-%EB%B9%84%EA%B0%9C%EB%B0%9C%EC%9E%90-ai/
- 관련 직무: HR·피플팀, 사내 운영
- 좋았던 이유: 구성원의 회의실 불편을 관찰한 뒤 직접 해결책을 만들고, 개인정보 범위 문제와 낮은 사용률을 겪으며 수정하고 운영한 과정을 보여줍니다. 피플팀의 사용자는 구성원이라는 관점과 실제 후속 자동화 업무까지 연결됩니다.
- 추출한 특성: 직무의 추상적인 역할보다 **누구의 어떤 불편을 발견하고, 시행착오를 거쳐, 어떻게 운영까지 책임졌는지** 보여주는 자료가 좋습니다.

### 7. 토스 Product Designer (Tools)는 무슨 일을 할까?

- 링크: https://toss.im/career/article/product-designer-tools-interview
- 관련 직무: Product Designer (Tools), 사내 업무 개선
- 좋았던 이유: 내부 사용자의 업무를 직접 관찰하고, 복잡한 운영 절차의 근본 원인을 찾아 제품과 자동화로 개선하는 여러 사례가 담겨 있습니다. 사용자 인터뷰, 도메인 학습, 다른 직무와의 협업, 결과 확인까지 실제 역할의 범위가 드러납니다.
- 추출한 특성: **현업 관찰 → 근본 원인 파악 → 해결책 설계 → 적용과 결과 확인**이 연결되는 자료를 우선합니다.

## 공통으로 발견한 좋은 자료의 특성

### 가장 중요한 기준

- 현직자가 실제로 맡은 문제와 책임 범위를 설명합니다.
- 핵심 업무와 반복 업무가 어떤 순서로 이루어지는지 알 수 있습니다.
- 단순한 결과보다 판단의 근거, 고민과 선택의 이유가 드러납니다.
- 문제 발견부터 실행, 협업, 검증 또는 운영까지의 흐름을 확인할 수 있습니다.
- 성공뿐 아니라 제약, 실패, 예상하지 못한 문제와 수정 과정도 보여줍니다.

### 있으면 좋은 구체성

- 사용하는 문서, 도구, 회의, 데이터 등 실제 업무의 흔적
- 함께 일하는 대상과 의견을 조율하는 방식
- 사용자·고객·구성원 또는 사업에 미친 변화
- 업무를 하며 생긴 어려움과 우선순위 사이의 선택
- 해당 직무가 단순한 직무 소개와 달리 실제로 무엇을 책임지는지 보여주는 설명

구체적인 숫자는 있으면 도움이 되지만 필수 조건으로 사용하지 않습니다. 공개하기 어려운 현업 자료에서는 숫자보다 업무 맥락, 고민과 판단 과정이 더 중요한 근거가 될 수 있습니다.

## 수집 기준에 반영할 초안

후보 자료가 아래 질문에 의미 있는 답을 주는지 확인합니다.

1. 이 자료를 읽으면 MD 또는 HR이 실제로 해결하는 문제를 알 수 있는가?
2. 핵심적이거나 반복적인 업무의 과정과 책임 범위를 알 수 있는가?
3. 현직자가 무엇을 고민하고 어떤 기준으로 선택하는지 드러나는가?
4. 다른 직무·부서·고객·구성원과 어떻게 협업하는지 알 수 있는가?
5. 실행 이후의 검증, 운영, 실패 또는 개선 과정이 있는가?

모든 질문을 충족할 필요는 없습니다. 다만 직무명만 언급하거나 기업문화와 성과를 홍보할 뿐, 실제 업무·문제·판단을 거의 알 수 없는 자료는 직무 학습 자료에서 제외합니다.

## 적용 시 주의할 점

- 기업 공식 콘텐츠는 현직자의 구체적인 사례를 얻는 데 유용하지만 채용 홍보 목적이 섞일 수 있으므로, 기업에 대한 긍정적 평가를 그대로 일반화하지 않습니다.
- 한 회사의 일하는 방식을 해당 직무 전체의 표준으로 단정하지 않습니다.
- 오래된 자료도 직무의 본질과 업무 과정을 공부하는 목적이라면 활용할 수 있지만, 현재 조직·도구·채용 절차에 관한 내용은 최신 사실로 취급하지 않습니다.
- 레퍼런스와 같은 직무나 주제만 찾지 않고, 위에서 추출한 질적 특성을 MD·HR 자료에 적용합니다.
